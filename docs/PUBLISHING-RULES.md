# Правила публикации

Правила одинаковы для всех пакетов в любом namespace. Клиент проверяет их
заранее, чтобы автор не тратил время на сборку и загрузку, но **реестр обязан
проверять их повторно**: клиентская проверка — удобство, а не доверенная
граница.

Проверить пакет, ничего не собирая:

```sh
yam-publish check --source ../my-player
```

Те же правила выполняются автоматически в `yam-publish pack` и
`yam-publish release`. `yam-publish publish` загружает уже подписанный архив и
полагается на проверку, выполненную при сборке; архив после `pack` менять
нельзя.

Код ошибки (`PKG00N`) стабилен: на него можно ссылаться в CI и в issues.

## Идентификация пакета

| Код | Правило |
| --- | --- |
| `PKG001` | `name` имеет вид `<namespace>/<name>`. Каждая часть — `a-z`, `0-9`, `-`, длина 1–63. Верхний регистр, `_`, `.` и `/` внутри части запрещены. |
| `PKG002` | `version` — SemVer (`1.2.3`, `1.2.3-rc.1`, `1.2.3+build.1`). Сокращения `1.2` и ведущий `v` недопустимы. |
| `PKG003` | Обязательны непустые `license` и `description`; `homepage`, если указан, — абсолютный `http(s)` URL. `description` — до 500 символов: он становится summary в каталоге. |
| `PKG011` | `permissions` — непустые уникальные токены без пробелов, до 100 символов. |

`namespace` выдаётся один раз и не переименовывается: имя пакета —
устойчивый идентификатор, по нему строится путь установки и база YAM.
Пространство `yam` зарезервировано за официальными пакетами проекта; загружать
в него может только владелец реестра.

## Платформы и артефакты

| Код | Правило |
| --- | --- |
| `PKG004` | `targets` не пуст, без дублей и пробелов; каждый конкретный target — существующий профиль из `platforms/`. `any` нельзя смешивать с конкретными target. |
| `PKG006` | Артефакт с итоговым target `any` не содержит native binary и файлов с executable-битом. `any` — только для платформонезависимых данных. |

Для каждого target публикуется отдельный `.yampkg`; один архив не может
обслуживать разные архитектуры. `armv7`-бинарник нельзя выдавать за `aarch64`
или `any`.

## Содержимое архива

| Код | Правило |
| --- | --- |
| `PKG005` | Пути payload безопасны и однозначны (см. ниже). |
| `PKG008` | Соблюдены лимиты архива. |
| `PKG009` | В payload нет секретов и служебных каталогов. |
| `PKG010` | `postinstall` и `services` ссылаются только на файлы этого пакета. |

`PKG005` покрывает:

- только относительные пути без `..`, `.` и абсолютных компонентов;
- разделитель — `/`; `\` отклоняется, чтобы сборка на Windows и Linux давала
  одинаковый архив;
- источник обязан находиться внутри каталога пакета (симлинк наружу
  отклоняется);
- каталог-источник требует destination с завершающим `/`;
- симлинки в payload запрещены; архив содержит только обычные файлы;
- дубли destination запрещены;
- для namespace вне `yam/` каждый путь `share/...` содержит компонент,
  начинающийся с `<namespace>.` (например,
  `share/host/plugins/author.player/main.lua`). Так пакет не засоряет общий
  каталог чужого хоста.

`PKG008` повторяет лимиты установщика: не более 64 МиБ в сжатом архиве,
256 МиБ распакованных данных, 64 МиБ на файл и 10 000 записей. Лимит сжатого
архива проверяется после `pack`.

`PKG009` — эвристика, не гарантия: проверяются имена (`.git/`, `.ssh/`) и
содержимое файлов до 4 МиБ (PEM private key, `YAM_PUBLISH_TOKEN=`, GitHub
токены). Если секрет оказался в опубликованном архиве, недостаточно выпустить
новую версию: отзовите токен или ключ.

`PKG010` требует, чтобы первый элемент `postinstall` и первый элемент
`services.*.exec` был путём `bin/...` из payload, а ключи `env` — `A-Z0-9_`.
Hook выполняется от root; это самая опасная часть пакета, и она проходит
модерацию отдельно.

## Зависимости

| Код | Правило |
| --- | --- |
| `PKG007` | Записи `depends`, `recommends`, `enhances`, `conflicts`, `replaces`, `provides` уникальны, синтаксически корректны и не ссылаются на сам пакет. |

Ограничения версий — `=`, `>=`, `<`, `<=`, `^`, `~` или их комбинация через
пробел. `depends` обязателен для установки; `recommends` не устанавливается
автоматически; `replaces` должен быть осознанным и объяснён в описании
изменений.

## Версии и неизменяемость

Опубликованная комбинация **имени, версии и target неизменяема**. Нельзя
перезаписать архив, исправить manifest или переподписать ту же версию. Ошибка
исправляется новой SemVer-версией (`1.0.1`, `1.1.0`, `2.0.0`). Это правило
проверяет реестр; yamreg возвращает `400` с причиной `immutable`.

Pre-release (`1.2.0-beta.1`) публикуется отдельно и не выбирается при
установке без явной версии.

## Подпись и авторство

- Загрузка подписывается Ed25519-ключом namespace; подпись связывает имя,
  версию, target и SHA-256 архива.
- Publish-токен не заменяет подпись и не даёт права выпускать пакеты от
  чужого namespace.
- Приватный ключ и токен не попадают ни в архив, ни в Git, ни в логи CI.
- `homepage` и исходники указывают на тот код, из которого собран архив.
  Изменения чужого кода отмечаются в описании релиза.

## Модерация

В текущем yamreg версии публикуются сразу. Остальная часть раздела относится только к реестрам с расширением модерации. В таких реестрах новые версии попадают в очередь. Реестр должен вернуть
`submission.id`, а `yam-publish status --watch` показывает переходы
`pending → in_review → approved | rejected` с причиной отказа. Пока заявка не
одобрена, версия не появляется в подписанном индексе и не устанавливается
пользователями.

Модератор проверяет:

1. соответствие имени, версии и target заявленному содержимому;
2. отсутствие секретов, вредоносных hook и необъявленных прав;
3. лицензию и право публиковать бинарники третьих сторон;
4. работоспособность на заявленных моделях (или явное указание, что проверка
   не проводилась);
5. понятность описания и changelog.

Причина отказа возвращается автору в machine-readable виде; повторная
загрузка отклонённой версии невозможна — нужна новая версия.

## Что проверяет реестр дополнительно

Клиент не может проверить это локально, поэтому ответственность на реестре:

- права токена и владение namespace;
- уникальность `(name, version, target)`;
- соответствие подписи загруженному архиву;
- лимит размера архива, целостность файлов и допустимость target для этого сервера;
- запись артефакта и пересборка подписанных индексов.

Наличие локального профиля не гарантирует поддержку target сервером. Например, yamreg на `f7da458` явно отклоняет `saturn`.

Изменение правил публикации — изменение контракта. Оно сопровождается новой
версией этого документа и, если правило ужесточается, периодом, в течение
которого существующие пакеты не блокируются без предупреждения.
