# API реестра: публикация и модерация

Контракт для сервера `repo.yse.wtf` и любого совместимого реестра. Клиент —
`yam-publish` (и десктопный `yam`). Базовый URL — `<origin>/api/v2`; автор
настраивает только endpoint загрузки `<origin>/api/v2/upload`, остальные пути
выводятся из него.

Контракт аддитивный: клиент игнорирует неизвестные поля и считает неизвестный
статус модерации промежуточным, поэтому сервер может добавить состояние, не
ломая старые версии. Удалять поля и менять смысл существующих нельзя без
нового префикса API.

## Авторизация

Публикация и чтение заявки требуют publish-токен:

```http
Authorization: Bearer <publish-token>
```

Токен выпускается в профиле автора и показывается один раз. Он не заменяет
подпись артефакта: сервер обязан проверить и токен (кто загружает), и подпись
Ed25519 (что именно загружено и от чьего имени).

Ошибки авторизации: `401` — токен отсутствует/недействителен; `403` — токен
действителен, но не владеет namespace или действие запрещено. Клиент при
таких ошибках не повторяет запрос.

## POST /api/v2/upload

Загружает один артефакт. Тело — ровно байты `.yampkg`, без multipart и без
сжатия транспортом.

| Заголовок | Обязателен | Значение |
| --- | --- | --- |
| `Authorization` | да | `Bearer <token>` |
| `Content-Type` | да | `application/octet-stream` |
| `x-yam-name` | да | `<namespace>/<name>` |
| `x-yam-version` | да | SemVer-версия |
| `x-yam-target` | да | ID платформы или `any` |
| `x-yam-sha256` | да | SHA-256 тела в нижнем hex |
| `x-yam-author-key` | да | `ed25519:<base64 public key>` |
| `x-yam-author-signature` | да | Base64 Ed25519-подпись |

Подписывается точная строка:

```text
yamreg-upload-v1
<name>
<version>
<target>
<sha256>
```

Сервер проверяет: токен, владение namespace, ключ принадлежит namespace,
подпись, SHA-256 и размер тела, правила публикации, отсутствие
`(name, version, target)` в индексе.

Ответы:

| Код | Значение |
| --- | --- |
| `201`/`202` | Принято; тело — объект заявки (ниже) |
| `200` | Идемпотентный повтор идентичной загрузки; тело — та же заявка |
| `400` | Некорректные заголовки или архив |
| `401` | Нет или неверный токен |
| `403` | Токен не владеет namespace |
| `409` | Версия уже опубликована или заявка на неё уже существует с другим архивом |
| `413` | Превышен лимит размера |
| `422` | Нарушены правила публикации; `error.details` — список кодов `PKG00N` |
| `429` | Слишком много запросов; `Retry-After` |
| `5xx` | Временная ошибка сервера; клиент повторяет с backoff |

Тело ошибки:

```json
{
  "error": {
    "code": "version_exists",
    "message": "author/player 1.0.0 for yandexmini_2 is already published",
    "details": ["PKG002"]
  }
}
```

`message` показывается автору как есть: он должен объяснять, что исправить
(поднять версию, сменить ключ, дождаться модерации), а не просто «rejected».

Успешный ответ:

```json
{
  "submission": {
    "id": "sub_01JABCDEF",
    "name": "author/player",
    "version": "1.0.0",
    "target": "yandexmini_2",
    "status": "pending",
    "created_at": "2026-11-16T18:00:00Z",
    "updated_at": "2026-11-16T18:00:00Z",
    "moderation": {
      "state": "pending",
      "reason": null
    }
  }
}
```

`submission` можно вернуть и в плоском виде (`id`, `status`, `reason` в
корне) — клиент принимает оба варианта. Если сервер не поддерживает
модерацию, допустим любой успешный ответ без `id`; клиент считает артефакт
опубликованным и сообщает, что следить не за чем. Это совместимость с текущим
реестром, а не рекомендуемый режим.

Идемпотентность: повтор той же комбинации `(name, version, target, sha256)`
возвращает существующую заявку, а не создаёт новую. Другие байты для той же
версии — `409`; перезапись запрещена.

## GET /api/v2/submissions/{id}

Возвращает текущее состояние заявки. Требует тот же Bearer-токен; автор видит
только свои заявки (`404`, если заявка чужая или не существует).

```json
{
  "submission": {
    "id": "sub_01JABCDEF",
    "name": "author/player",
    "version": "1.0.0",
    "target": "yandexmini_2",
    "status": "in_review",
    "created_at": "2026-11-16T18:00:00Z",
    "updated_at": "2026-11-16T18:07:31Z",
    "moderation": {
      "state": "in_review",
      "reason": null,
      "moderator": "registry-team"
    }
  }
}
```

Состояния:

| Состояние | Терминальное | Значение |
| --- | --- | --- |
| `pending` | нет | Заявка в очереди |
| `in_review` | нет | Модератор проверяет |
| `approved` | да | Одобрено, публикация в процессе |
| `published` | да | Артефакт в подписанном индексе |
| `rejected` | да | Отклонено; `moderation.reason` обязателен |

Переходы: `pending → in_review → approved → published` либо
`pending|in_review → rejected`. Обратные переходы запрещены. `approved`
означает решение, `published` — факт появления в `/v2/index.json`; клиент
считает успехом оба, но «живая модерация» должна показывать разницу, если
публикация индекса задерживается.

Клиент опрашивает endpoint с интервалом по умолчанию 5 секунд и таймаутом
15 минут (`--interval`, `--timeout`). Повторяет только `429`/`5xx`/сетевые
ошибки, максимум три раза подряд; `401`, `403`, `404` и неизвестный формат
ответа прекращают ожидание сразу.

После `rejected` повторная загрузка той же версии невозможна. Автор исправляет
пакет, поднимает SemVer и создаёт новую заявку. Причина отказа хранится в
журнале модерации и доступна автору бессрочно.

## Публикация индекса

Индекс обновляется только после `approved`:

- артефакт и подпись индекса пишутся атомарно (временный файл + rename);
- версия появляется в `/v2/packages/<namespace>/<name>/index.json` и в
  `latest` каталога одновременно;
- `published_at` — время фактической публикации, а не загрузки;
- при ошибке записи заявка остаётся `approved` и повторяется, а не теряется;
- отозванная версия (`yanked`) остаётся в истории, но не выбирается
  резолвером и явно помечается в индексе.

## Безопасность

- Токены и подписи никогда не попадают в URL, логи и тела ошибок.
- Сервер не доверяет клиентской проверке `PKG00N` и повторяет её сам.
- Ограничения размера проверяются до буферизации тела.
- Архив после `approved` неизменяем; хранение должно быть append-only.
- Модерация не заменяет проверку подписи: вредоносный архив с валидной
  подписью отклоняется модератором, а не пропускается автоматически.
- Причина отказа — данные модератора, а не автора: не исполнять и не
  рендерить как HTML.
